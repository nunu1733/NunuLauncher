### 8. (round-5 record) Owner re-review round 2: the widget invariant key now compares in its typed canonical order

Round 5 re-anchors after the owner re-review confirmed both round-4 conditions resolved and returned one new Medium, fixed by `f7b900e365` and re-verified by the auditor at this head:

- **The defect.** The widget stream ordered its stream by the concatenated `targetKeySortValue` string (`"3:provider:appWidgetId"`), which has two spec-10-conformance problems: the `appWidgetId` segment compared lexicographically ("10" < "2"), and the profile segment was absent entirely — two widgets with the same provider/appWidgetId on different profiles fell through to the `ItemId` tie-break. This record's round-2/3/4 text had described that encoding as "the pre-existing canonical encoding"; it is the pre-existing *string encoding* (used by the app/folder/category streams, whose target keys carry no integer-code segment), but it is not a spec-10-conformant comparator for the widget key, and the round-4 AC-5 text is corrected accordingly (see the rewritten AC-5 bullet).
- **The fix, verified against the types.** The comparator now compares `(WidgetKey.provider, WidgetKey.appWidgetId, WidgetKey.profile)` via the typed `compareTo` implementations — `ComponentKey.compareTo` and `ProfileId.compareTo` are `compareUtf8Bytes` (UTF-8 byte order, `Identity.kt`), `AppWidgetId.compareTo` is numeric (`value.compareTo` over `Int`) — before the `ItemId` tie-break, matching spec 10's canonical ordering (integer codes numerically, text handles by UTF-8 byte order). The unchecked casts are safe: the kind/target consistency validation (`KIND_TARGET_MISMATCH`, the V-12 family) rejects any widget kind whose target is not a `WidgetKey` before planning. Every segment is relocation-invariant, so the spec's idempotence proofs (D-2/D-3) are unaffected — confirmed by the discriminator fixtures' replan-empty-diff checks and by `CrossStrategyCorpusTest` remaining green.
- **Spec clarification.** Spec 235's common rules now state the typed order explicitly and forbid the concatenated-string comparison, with a dated change-history correction row — the accepted-spec normative text and the implementation now say the same thing.
- **Discriminator fixtures.** `tidyV2WidgetKeyOrdersAppWidgetIdNumericallyNotLexicographically` (same provider/profile, appWidgetId 2 vs 10, ItemIds reversed relative to numeric order — under the withdrawn string encoding the two first-fit cells would swap) and `tidyV2WidgetKeyOrdersProfileBeforeItemId` (same provider/appWidgetId across profiles pa/pb, ItemIds reversed — the profile segment must decide), each with replan-empty-diff.
