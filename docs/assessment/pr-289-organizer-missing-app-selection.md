## Findings

Pass-with-findings — no blocking findings. The four owner findings are resolved as claimed; the items below are follow-up observations that do not weaken the layout-data safety properties.

### 1. (judgment, non-blocking) Unplaced candidates × materializer exact-set partition: fail-closed, but the unplaced rows are not itemized anywhere user-visible

Mechanism traced end-to-end: a scope-composed plan with `STRATEGY_SCOPE_FULL` candidates is `Planned` with non-empty `Planned.unplaced`; the materializer requires `candidatePlacements.map{it.item}.toSet() == candidateById.keys` (OrganizationPlanMaterializer.kt L122), so such a plan returns `Result.Invalid` → `inspectPlan` maps it to `NotPlannable(MATERIALIZATION_INVALID)` → the run finishes in `State.PlanningRejected(IMPOSSIBLE)` — the **same terminal state the existing unplaced contract produces** (validation-level `EXCEEDS_GRID_DIMENSIONS`/`TARGET_UNAVAILABLE` surface as `Rejected.Impossible` → the same `PlanningRejected(IMPOSSIBLE)`). Nothing is created or written, and the AC-14 concrete-preview gate independently prevents confirm. **Judgment: consistent and acceptable** — the spec §5 overflow contract ("警告表示され、作成も行われない") is observably discharged as a typed plan-level failure with zero writes, exactly like the pre-existing unplaced reasons; a partially-placed Add plan is never confirmable. Residual gaps, recommended as a small follow-up (not a merge blocker): (a) `Summary.unplacedByReason` folds only `Rejected.Impossible.unplaced`, so `STRATEGY_SCOPE_FULL` rows carry no per-candidate breakdown in the rejection screen — `unplacedReasonString(STRATEGY_SCOPE_FULL)` (ManualOrganizationPreferences.kt L1310) is currently unreachable, added only because the `when` must be exhaustive; (b) the diagnostics `PLANNED` event hardcodes `unplacedCount = 0` with a now-stale comment ("Planned has no unplaced items", PlanningProjection.kt L98), so the journal under-reports; (c) the corner where all candidates are unplaced and no other change exists ends in `State.NoChanges` with no explanation. Minor nuance also recorded: under an injected `AllocationFault`, a `CAPTURED_PAGE_ONLY` strategy manifests the fault as unplaced rows rather than the loud `error()` used by `CAPTURED_THEN_NEW`/`PREFERRED_THEN_NEW` — acceptable (test-only injection; the within-scope null is precisely the page-local strategy's designed outcome).

### 3. (minor, contract-nuance) Resolver catch is `RuntimeException`-only; the checked `RemoteException` family is not covered

`AndroidCandidateApplicationResolver.resolve` wraps the entire platform read, but catches `RuntimeException`, while `LauncherApps.getActivityList` declares `throws RemoteException` (`DeadObjectException`/`TransactionTooLargeException` are checked, not RuntimeException subclasses) — a binder failure during system-server death would still escape `resolve`, so plan §4's literal "例外を上位へ出さない" has this residual hole. Context: the accepted detection source (`AndroidMissingAppCandidateSource.detect`) guards the suspension-flag read only and leaves the same `getActivityList` call unguarded entirely, so the fix is strictly stronger than the seam it rides, and RuntimeException covers the common device-facing label/icon/binder-stub failures. Recommend a one-line follow-up widening the catch (or an explicit note in the plan) rather than blocking: an escaping exception aborts the run via the run-level `catch (Throwable)` boundary (`abort` → `State.Cancelled`) without any write.

### 4. (minor, test gap) No run-level unit test pins `State.CandidateResolutionFailed`

The materializer→typed-failure mapping and the UI mapping (re-detect retry, zero-write copy) exist, but `ManualOrganizationRunTest` has no case driving `confirm()`/preview through `Result.CandidateResolutionFailed` to assert the state transition and zero-write property the way other terminal states are pinned. Compiler exhaustiveness plus the materializer-level tests bound the risk; recommend adding the case in a follow-up.
