# PR #321 — U-5 probe evidence (probe completion conditions (a)–(d))

Issue #203 / spec `specs/203-usage-implicit-preference-signals/spec.md` U-5.
Probe implementation: `tests/organizer-instrumentation/app/lawnchair/organizer/UsageStatsIntervalProbeTest.kt`
(tag `U5Probe`), run against an API 36 emulator (`emulator-5554`, sdk_gphone64_arm64).

- Probe execution date: 2026-09-15
- Instrumentation runner: `app.lawnchair.migration.DeckRetirementTestRunner` (extends `AndroidJUnitRunner`)
- Usage access was granted to the app under test via `adb shell appops set app.lawnchair.debug GET_USAGE_STATS allow` (app-op based, matching the production permission model)
- Real usage data generated by launching system apps (`com.android.settings`, calculator) before the runs

## (a) `queryUsageStats(INTERVAL_DAILY)` interval boundaries / granularity

Observed (Asia/Tokyo run, 697 intervals; Pacific/Midway run, 698 intervals):

- **Intervals are ~24h rolling buckets, not local calendar-day buckets.** Only
  267/697 (Tokyo) and 268/698 (Midway) intervals had `firstTimeStamp` and
  `lastTimeStamp` on the same local calendar day. The majority span two
  calendar days, e.g.:
  `pkg=com.google.android.youtube first=2026-09-10(1789000623659) last=2026-09-11(1789087023658)`
  (a 24h span starting at ~09:57 local, not midnight).
- Current-day intervals start at the first data timestamp of the day (device
  boot/setup time), not at local midnight.
- `crossBegin=0`, `crossEnd=0` in both runs — intervals did **not** extend
  beyond the requested `[begin, end]`.
- Foreground data present: `nonZeroFg=19` intervals with
  `totalTimeInForeground > 0`.

## (b) Full-containment filter against real data

- `partialIn30dWindow=0`: every returned interval is fully contained in the
  requested 35d query range and in the 30d window.
- **However**, because the intervals themselves cross local calendar days
  (430/697 non-aligned), a full-containment filter keyed to **local calendar
  day windows** would drop the majority of intervals (every interval that
  crosses midnight). The accepted contract's premise — `INTERVAL_DAILY`
  returns local-calendar-day buckets where partial-edge exclusion is a
  boundary-day undercount only — is **refuted** by this measurement.
- Consequence: spec U-5 window semantics are amended before merge (see
  "Deviation and contract amendment" below), as the accepted contract requires
  when a probe detects a deviation.

## (c) 30-day retention availability

- The API accepted a 35-day query window and returned data; observed data on
  this emulator covers ~9 days (`retentionDaysApprox=9`, emulator lifetime).
- Platform retention is device-dependent (known limitation already recorded in
  the spec); the API contract accepts the 30-day window and returns whatever
  the platform retains. No API error or truncation signal was observed.

## (d) Launcher-origin day anchor under timezone change / DST

Same instant re-probed under three device timezones (via
`adb shell cmd alarm set-timezone ...`):

| Device timezone | Probe log time | `zone=` | `anchorEpochDay` | DST state |
|---|---|---|---|---|
| Asia/Tokyo | 09-15 14:50 | Asia/Tokyo | 2026-09-15 | `isDaylightSavings=false` |
| America/New_York | 09-15 01:53 | America/New_York | 2026-09-15 | `isDaylightSavings=true`, `nextTransition=Overlap at 2026-11-01T02:00-04:00 to -05:00` |
| Pacific/Midway | 09-14 18:54 | Pacific/Midway | **2026-09-14** | `isDaylightSavings=false` |

The epoch-day anchor is projected from the device's **current** timezone and
moves across the date boundary with it (Tokyo 09-15 vs Midway 09-14 for the
same instant). This matches the accepted contract: the day anchor is the
device-local calendar day, and a timezone change is naturally followed on the
next capture because the anchor is persisted per launch, not projected
forward. DST state is reported and the anchor projection is unaffected beyond
the ordinary calendar-day boundary.

## Deviation and contract amendment (spec change before merge)

Per the accepted contract ("逸脱が確認された場合は、当該実装 PR の merge 前に
spec 変更で契約を修正する"), the following amendment is applied in this PR:

1. **Window semantics**: `queryUsageStats(INTERVAL_DAILY, anchor − N·24h,
   anchor)` (rolling 24h windows, not local calendar days). All returned
   intervals are aggregated **as-is** — no partial-edge filtering. The probe
   showed intervals do not extend beyond the requested range
   (`crossBegin=crossEnd=0`) and are consecutive non-overlapping buckets, so
   the sum is faithful; a calendar-day containment filter would have dropped
   the majority of intervals (430/697).
2. **Active-days**: approximated as the number of returned intervals with
   `totalTimeInForeground > 0` in the 30d query (one active-day per ~24h
   bucket), capped at 30.
3. **Recency / rank universe**: unchanged semantics (max `lastTimeUsed` over
   returned intervals; rank universe = launchable apps with at least one
   foreground-carrying interval in the window), now stated against the
   observed interval semantics.
4. **7d window**: a separate `queryUsageStats` call with `[anchor − 7·24h,
   anchor]`; the 7d universe and totals come from that query's own intervals.
5. **Launcher-origin day anchor**: unchanged (device-local calendar day,
   timezone-following — confirmed by (d)).

Determinism is preserved: the same usage data + the same window anchor + the
same query ranges produce the same aggregates and digest.
