## Criteria check

- **Spec §GLOBAL_COMPACT_V1 rule 1 — eligible set is movable `1×1` singletons only; non-`1×1` movables and all existing folder units are `STRATEGY_PRESERVED` fixed occupancy constraints — PASS.** The registry filter requires kind `APPLICATION`/`DEEP_SHORTCUT` **and** workspace span `GridSpan(1,1)`. The closed movable-kind analysis: `movableItems` = items with `determinePreservation == null`, which (given `PlanningValidation` rejects `Unknown` kinds and `UnsupportedContainer` placements, and `determinePreservation` preserves legacy shortcuts, widgets, app pairs, dock, folder members, locked, unavailable, reserved-overlap, non-target) can only be `APPLICATION`, `DEEP_SHORTCUT`, or top-level `FOLDER` workspace items — so `strategyFixed` is exactly the spec's fixed set, and the `as CapturedPlacement.Workspace` cast is total on it (same invariant the child-4 executor relies on). Each fixed unit is `markOccupied` at its captured cell before any allocation and reported `Preserved(STRATEGY_PRESERVED)` with its captured target (truthful reason per §Strategy-preserved rationale; never `ALREADY_CANONICAL`/`NON_TARGET`).
- **Spec §GLOBAL_COMPACT_V1 rule 3 — global unit order `(PageOrder, PageId, cell.y, cell.x, ItemId)` — PASS.** `workspaceUnits` is sorted by exactly that 5-key comparator: `pageOrderOf` reads `context.pageOrderMap` (built in `PlanningPlacement.place` from `input.snapshot.pages` as `id → order`), then `pageId`, then `cell.y`, then `cell.x`, then `ItemId`. `checkDuplicatePages` (V-… `DUPLICATE_PAGE`) rejects both duplicate page ids and duplicate page orders before placement, so `PageOrder` is unique per page and the `PageId` key is a redundant-but-harmless tie-break; `ItemId` is unique per `checkDuplicateItemIds`, making the order total and deterministic. Folder members are excluded from the singleton stream via `folderMemberIds`, so no unit is both workspace-placed and folder-absorbed (no double placement).
- **Spec §GLOBAL_COMPACT_V1 rule 2 — folder formation is canonical P-04/P-05 applied to the eligible `1×1` candidates only — PASS.** `formFolderGroups` is the shared canonical grouping/partition policy (same-profile same-category grouping, capacity partition, ranks, `NewFolder` semantics, fallback/min-group skips) and its `candidates` argument is built solely from `eligible` — a non-`1×1` app has no path into folder candidacy under this strategy, so the spec's "never simultaneously `STRATEGY_PRESERVED` and absorbed" condition holds structurally. Formed folders are placed after the entire singleton stream, sorted `(preferred page key, NewFolderOrdinal)`; `preferredPageOf` computes the earliest member page with the same `pageRefComparator` expression the canonical executor uses for new-folder preferred pages, and — because `PageOrder` is unique — comparing by `pageOrderOf(preferredPage)` is equivalent to the full preferred-page key. Members receive `Moved(FOLDER_MEMBER)` at `(NewFolderRef(ordinal), rank)` with ranks in the canonical member order, identical to the canonical/incremental folder-member emission.
- **Spec §GLOBAL_COMPACT_V1 rule 4 — page scope: scan all captured pages by `PageOrder`, then already-created new pages, then create another page; no empty-page deletion — PASS.** Allocation runs exclusively through `Allocator.allocateCapturedThenNew`, which iterates `capturedPages` (sorted `(order, id)` in `place`) then `newPages` in creation order, then appends a new page with `order = maxCapturedOrder + 1 + k`. This is the proven incremental-run semantics now executed on the full-run stream; `PageScope.CAPTURED_THEN_NEW` is honored (the executor's hardcoded call matches the registered declaration). Cell order is `TOP_LEFT_ROW_MAJOR` first-fit via the shared `findRowMajorFirstFit` (single occupancy/bounds implementation preserved; no second allocator added). `buildNewPages()` is the only page-list output; no page-record deletion exists anywhere in the planning module (spec Non-goals honored).
- **§Idempotence arguments — GLOBAL_COMPACT_V1 — PASS (independently re-derived + test-verified).** The strategy is a sorted assignment: units in global visual order consume the sorted free-cell list (captured-page order, then row-major) because each unit takes the earliest free cell at its turn and occupancy is monotone, so assigned cells are strictly increasing in scan order; folders then take the next free cells (the tail). After materialization the singletons' captured visual order equals their assignment order, and the formed folders — now captured `FOLDER` units — join `strategyFixed` (verified: kind `FOLDER` fails the eligible filter and is movable, so it is marked occupied + `STRATEGY_PRESERVED`), while their members become `FolderMember` placements preserved as `STRUCTURAL` (never re-fed into grouping). Run 2's free list is run 1's free list minus the folder cells, whose first k entries are exactly the singleton cells, so every singleton reclaims its own cell (`ALREADY_CANONICAL`) and nothing moves. New pages created in run 1 are captured in run 2 with orders after all original pages, preserving the scan order; run-2 new pages continue the order sequence. `nonSquareMovableUnitsAreStrategyPreservedAndNeverCompact` and `foldersFormOverEligibleCandidatesOnlyAndArePlacedAfterTheSingletonStream` both materialize and replan through the public seam asserting zero `Moved` (and, in the folder case, zero new folders).

## Findings

1. **Low — stale phrase in the spec's idempotence bullet (non-blocking, documentation).** Spec 182 §Idempotence arguments (GLOBAL_COMPACT_V1) says the counterexample's "only the `1×1` app compacts, moving from page 2 into the earliest free page-1 cell", but the normative fixture geometry in the same bullet and in §GLOBAL_COMPACT_V1 rule 5 / the "preserves non-square" scenario places the `1×1` app on **page 1** at `(2,1)` (it is the `1×2` that sits on page 2, and page 2's unit never moves under the accepted strategy). The implementation and the test follow the unambiguous fixture geometry and the scenario wording ("compacts onto page 1"): the `1×1` moves within page 1 from `(2,1)` to the earliest free cell `(0,0)`. This reads as a leftover from the pre-fourth-review fixture (before the `1×1` was added at `(2,1)`). Per AGENTS.md the contradiction should be recorded on the Epic Issue and the canonical spec wording fixed; no behavioral impact.
2. **Low — counterexample folder-candidacy assertion is structurally satisfied but not behaviorally discriminated (non-blocking).** `nonSquareMovableUnitsAreStrategyPreservedAndNeverCompact` asserts `newFolders.isEmpty()`, but with no classification signals all units fall into the fallback category, which `formFolderGroups` skips regardless of span — so the assertion would pass even if non-`1×1` apps were folder candidates. The exclusion itself is structural (the only `formFolderGroups` call site feeds `eligible`, which requires `1×1`), and the code path is unambiguous; a future contrast case (a `2×1` GAMES app alongside `1×1` GAMES apps asserting the folder forms from the `1×1`s only) would make the normative "never a folder candidate" rule behaviorally visible. Suggested for Issue #219's fixture-matrix pass, not a merge blocker.
3. **Medium (tracked, non-blocking) — shared cross-strategy property/harness coverage and performance samples.** `PlannerContractHarnessTest`/`PlannerGeneratedPropertyTest`/`PlannerBenchmarkTest` remain pinned to `CANONICAL_PAGE_COMPACT_V1`; AC-9/AC-11/AC-12 execution for `GLOBAL_COMPACT_V1` (including the Issue #216 acceptance line's performance sample) is owned by Issue #219 (child 9 evidence matrix), whose body names the cross-strategy runner transfer from the PR #222 owner review — same disposition as children 4 and 5. Not a merge blocker for this child.
4. **Note — preview surface deferral is the accepted split.** The spec's "preview must surface the cross-page move count" for `GLOBAL_COMPACT_V1` is child 8 (#218) scope per its Issue body (`PreviewCounts` extension + strategy identity display); this PR correctly ships planning + policy only.
5. **Note — executor pageScope handling.** `executeGlobalCompact` calls `allocateCapturedThenNew` directly rather than branching on `strategy.pageScope` (the canonical executor branches). The registered declaration (`CAPTURED_THEN_NEW`) matches the call, so current behavior is spec-exact; a future `CAPTURED_VISUAL_GLOBAL` definition declaring a different page scope would silently inherit this executor's scope. Harmless under the curated-catalog rule (one definition per catalog member); worth a KDoc note if a second global-ordering strategy is ever proposed.
