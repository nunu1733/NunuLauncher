## Criteria check

Checked against the accepted spec `specs/58-serialize-runtime-restores/spec.md` (frontmatter `status: accepted`, verified in-repo) and the proposed target spec `specs/168-nova-restore-authoritative/spec.md` (scenarios S1–S5 and Acceptance, checked as prose):

- **AC-1 (one restore-family lease across replacement through reload) — preserved.** `convertAndRestore` acquires `BACKUP_RESTORE` via `acquireBlockingQuietly(...).use { ... }` inside `withContext(restoreDispatcher)`, and quiesce, staging, pref writes, `applyGridInfo`, the commit barrier, `restored.db` copy, `performRestore` and `reloadAfterRestore` all execute inside that one `use` block on the single dedicated thread. Acquisition and release are same-thread by construction (single-thread executor; the `Dispatchers.Main` hop inside `applyConvertedGrid` returns to the same dispatcher), so the thread-bound lease and the `tryReenterRestoreFamily` re-entry inside `performRestore` cannot deadlock — the exact failure the dedicated dispatcher was introduced to fix (`9bf4af9b8e` commit message and the code comment at the `restoreDispatcher` declaration).
- **AC-3 (ordinary writes cannot enter the replacement window) — preserved and strengthened.** The new `runDbCleanupExclusively` takes a short `MODEL_WRITER` lease when free, re-enters only for a same-thread `MODEL_WRITER` holder, and returns `false` for any other holder; restore acquisition (`acquireBlocking`) waits while `current != null`, so a restore either starts strictly before the cleanup section (which then sees the holder and skips) or blocks until the deletion completed. The check→delete TOCTOU of a snapshot check is closed structurally: the deletion runs while the section is held, and `cleanup.run()` performs no coordinator acquisition (file listing/deletion/logging only), so no nested wait and no deadlock; the reentry decrement cannot reach zero because only the owning thread can close the outer lease and that thread is inside the section. Release goes through the standard `LeaseImpl.close` → `release` path, so the deferred FIFO drain and `notifyAll` semantics are unchanged.
- **AC-7 (style and relevant suites pass on CI) — met.** CI run 33242295231 on the exact head: `check-style`, `organizer-unit-tests`, `build-debug-apk`, `validate-repo-contract` and all organizer-instrumentation lanes green, `final-status` success (API-verified above). Independently re-executed locally by this audit: `spotlessCheck`, both APK assemblies, and the targeted instrumentation classes — see Executed test surface.
- **Spec #168 Outcome 1 / Behavior 1–3 (authoritative grid application) — verified in code.** Order in `NovaBackupConverter.kt:197-211`: `gridState.writeToPrefs(context)` → `writeGridToLawnchairPrefs` (typed setters under `batchEdit`, values logged) → `applyConvertedGrid` (main thread, lease held) → `gridState.writeToPrefs(context, true)` (synchronous `commit()`). The barrier is a genuine durability barrier: `BasePreferenceManager.sp` and `DeviceGridState.writeToPrefs(context, commit)` both use `Utilities.getPrefs(context)` (`LauncherFiles.SHARED_PREFERENCES_KEY`), and `SharedPreferencesImpl.commit()` synchronously persists the whole in-memory map, including the values the batch's `apply()` had already installed there — so the grid values survive the restore's self-restart. The typed `IntPref.set` updates the in-memory cache at write time and the batch-end `invalidate()` forces re-reads from the fresh sp state, so any listener-posted recompute (the `hotseatColumns` `reloadGrid` listener is the #167 revert trigger) converges to the converted grid instead of reading stale rows/cols.

## Findings

No blocking findings. The merge may proceed once the repository gate (`high-risk-gate` workflow) accepts this record on the current head.

### Non-blocking 1 (resolved at `6bd20edf16`): spec Acceptance cited a build SHA that cannot compile standalone

`specs/168-nova-restore-authoritative/spec.md` recorded the physical Pixel 9a S1 run as "build `11d4074`". CI run 33240258887 on `11d4074f53` failed with a javac error in `LayoutWriteCoordinator.java:164` (fixed in `1c64b5f484`), so no APK could have been produced from that commit as pushed. The only plausible reading is a local build of `11d4074` plus the uncommitted compile fix — whose production code is byte-equivalent in behavior to the audited head (`1c64b5f484`'s production delta is exactly that compile fix; `bb188eea08` is docs-only). The device evidence is therefore credible against head-equivalent production code, but the citation was wrong. **Resolved in the re-audit pass:** commit `6bd20edf16` amends the spec Acceptance line to state that the device APK was built from a worktree whose production code is identical to `1c64b5f4` (that commit adds only the javac compile fix), citing this finding; the auditor verified the correction against the `1c64b5f484` compile-fix diff and the 33240258887 failure log, and confirmed it is docs-only.

### Non-blocking 2: emulator runtime evidence predates the two review follow-ups

The emulator S1/S4 run is recorded against build `9bf4af9`, which predates `runDbCleanupExclusively` and the synchronous commit barrier (`11d4074f53`). Runtime coverage of those two follow-ups rests on the device claim (Finding 1) plus the head-level instrumentation tests, which this audit re-executed green. The gap is narrow (the follow-ups strengthen exclusion/durability; the S1 outcome path is unchanged), but a one-restore emulator run on a head build would close it cleanly if the scenario is ever re-verified.

### Non-blocking 3: no raw evidence artifacts committed for #168

Unlike the issue-164 pattern (`docs/assessment/evidence/…` with journals), the #168 runtime evidence exists only as prose and log excerpts in the spec Acceptance and PR body. The claims are internally consistent with the code and the residual emulator state, but they are not independently re-checkable from the repository.

### Non-blocking 4: `hasActiveRestoreFamilyLease()` is production-dead after the follow-up

After `runDbCleanupExclusively` replaced the snapshot check, the accessor is used only by tests. It remains within the spec's declared scope (an accessor for "is a restore-family lease active") and is harmless, but per the repo's "no speculative seams" design rule it should either be documented as a test/observability seam or dropped in a follow-up.

### Non-blocking 5: deletion-path test has no live-app lease tolerance

`cleanUpDatabasesDeletesUnmatchedFilesWithoutRestore` asserts that cleanup deleted the sibling file, but unlike the lease test it does not retry against a transient non-restore holder (an organizer or other-thread `MODEL_WRITER` lease from the live app would make `runDbCleanupExclusively` return `false` and the assertion fail). Flake risk under app activity, not a correctness defect; the same retry pattern used elsewhere would harden it.

### Non-blocking 6: risk label absent on issue and PR

Neither #168 nor PR #169 carries `risk: layout-data`; the gate fired via the high-risk-path insurance clause (run 33242295230 log names the three production paths). `docs/project/github-workflow.md` makes label designation the primary trigger ("label指定が正本"), so the label should be added for consistency; the evidence requirement itself was correctly enforced regardless.

### Pre-existing, out of scope (noted, unchanged by this PR)

`cleanUpDatabases()` reads `idp.dbFile` before entering the exclusive section (same shape as pre-fix), and a `MODEL_WRITER` lease does not defer tokenless `MODEL_EXECUTOR` work — so a concurrent tokenless load could in principle observe a different live grid name than the one cleanup deleted against. This is baseline behavior outside #168's scope and is not weakened by the change; the restore window itself is fully excluded.
