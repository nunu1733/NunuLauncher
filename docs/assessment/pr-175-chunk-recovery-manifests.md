## Findings

No blocking findings. The merge may proceed once the repository gate (`high-risk-gate` workflow) accepts this record on the current head.

### 1. CW-AC-08 remains operator evidence — not certified here

The #171-device sequence (organize → exactly one Nova restore → organize → `APPLY_VERIFIED`) is the spec's mandatory device-class verification and is still open in the plan checklist. Real-SQLite evidence at device scale exists on the same-class Pixel 9a (recorded in the plan; the emulator re-runs above reproduce the same contract at head), but CW-AC-08 itself closes only when the operator executes the device sequence. This audit does not certify it.

### 2. Pre-existing smoke-script lease-contention race (out of scope, needs follow-up Issue)

`tools/organizer-recovery-smoke.sh` has a startup-reconcile lease-contention race that can surface `Unresolved(COMMIT_OUTCOME_UNKNOWN)` when the async startup resume races the scripted phase. It was reproduced on unfixed `main` (RESTORING phase) per the plan record, predates this PR, and is not introduced or worsened by this diff. A follow-up Issue is required (the plan already flags this); it must not be conflated with #174 evidence.

### 3. Gate-format limitation: `CW-AC-NN` IDs cannot be machine-cited

The spec's acceptance IDs (`CW-AC-01`…`CW-AC-10`) are invisible to the gate's `_REQUIREMENT_ID_RE` (hyphen-prefixed), so the `Criteria:` line carries ADR-0009/ADR-0003 and the spec criteria are verified in the body — the accepted PR-160/PR-165 pattern. Recommend a follow-up maintenance Issue to either extend the gate grammar to prefixed `*-AC-NN` families or rename spec IDs to a parseable form; until then, spec criteria for prefixed-ID specs are only human-verifiable at the gate.

### 4. Minor code observations (non-blocking)

- `RecoveryStore.kt` keeps an unused private `storedFromEncoded` helper (dead code after the closed-read refactor); harmless, drop in a follow-up.
- `RecoveryDbHelper` KDoc still says "Creates format 1" while `onCreate` now executes the schema-3 DDL — stale comment, not behavior.
- The spec test-oracle line "Quarantine fault injection rolls back and its tombstone uses canonical reason 6" is only partially covered: reason-6 persistence on real SQLite is proven (`unreadableChunkRecordIsQuarantinedWhenReadyAndPreservedWhenVerified` reads back the tombstone through the production mapper), and rollback atomicity of the exact shared primitive (`writeTombstone` → `deletePoint`) is fault-injected via the `RETENTION_TOMBSTONE`/`PRUNE_TOMBSTONE` cases, but no case injects a fault into the quarantine transaction itself. A dedicated `QUARANTINE_TOMBSTONE` fault case would close the letter of the oracle; the behavior is primitive-equivalent to the covered prune path.
- `validateChunkCoverage`'s `max_len` predicate is not a complete chunk-shape characterization (a hypothetical short-first/full-last swap would satisfy all five predicates), but that shape is unreachable from the `substr()` construction that generated the rows (chunk 0 is always full when size > L); the validation is defense-in-depth and its soundness for the construction is verified.

### 5. Interpretation documented: ApplyProtocol's non-`Readable` mapping

`ApplyProtocol`'s automatic-recovery helper maps every non-`Readable` result (including `Unreadable`) to the existing `ApplyResult.Unresolved` outcome rather than a `CORRUPT` rejection. The spec's `Unreadable → NotRestorable(CORRUPT)` mapping is stated for `recover()` (and preview parity), which the implementation satisfies exactly; the plan's caller rule ("`Unreadable` is a validation/store-corruption failure appropriate to each existing caller result") supports keeping the apply-internal path's pre-existing fail-closed `Unresolved` shape. Recorded as an interpretation, not a violation; no public result type changed.
