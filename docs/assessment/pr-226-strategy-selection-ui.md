- **Spec 182 §Preview integration "fresh compose/plan cycle" / spec 52 §Coordinator (no snapshot reuse) — PASS.** On a committed change while a run is active the code issues `dismiss()` then `start(trigger)`. `dismiss()` cancels only pre-admission operations (writes nothing; `applicationAdmitted` → `ApplicationInProgress` no-op), and `start()` always runs `application.composeFullOrganization()` — a fresh capture whose composer read observes the newly published snapshot; there is no in-run substitution path (the composer reads the store itself, `OrganizationInputComposer.kt:190–212`). During `Applying` post-admission, `dismiss()` returns `ApplicationInProgress` without state change and `start()` returns `Busy` (`beginOperation` sees `activeOperation != null`), so an in-flight application is never restarted — the safe side. Two quick taps converge through the same guards; the store serializes writes under its lock.

## Findings

1. **Blocking 1 — the picker regresses the spec 52 MFO-15 / spec 195 instrumentation suite on this exact surface; `final-status` is red on the audited head.** The six new picker items render above the run state and consume the viewport/focus budget the existing `ManualOrganizationPreferencesInstrumentationTest` relies on: 12 of its 22 tests fail deterministically (preview rows and Confirm/Cancel below the LazyColumn fold, traversal targets beyond `pressDownUntilFocused(maxPresses = 12)`, focus restoration racing the taller list). The PR adapted neither the screen nor those tests and did not run the connected lane (the PR body's test list stops at androidTest *compile*). This is also a real UX consequence, not only a test artifact: with the picker expanded, the primary review actions now sit below the fold on a phone viewport. Fix options (implementation's call, must keep the MFO-15 contract): collapse/compact the picker, move it behind an expandable section, or update the tests to scroll — with the requirement that required actions remain reachable without focus loss at 200% font scale. The high-risk gate additionally requires a green `final-status` on the fixed head before merge.
2. **Blocking 2 — TalkBack label announcement: `contentDescription` on the selectable row suppresses the strategy name.** `ManualOrganizationPreferences.kt` sets `.semantics { contentDescription = description }` on the same node that `selectable()` merges the name and description `Text` children into; Android accessibility clients read `contentDescription` **instead of** the node's text, so the announcement is "description, selected, radio button" — the name (primary label) is lost, violating spec 182 §Accessibility ("meaningful label/state/selection announcements") and the PR's stated "name + selected state + description as one node". Trivial fix: drop the `contentDescription` modifier (both `Text`s are already merged into the announcement) or set it to `"$name. $description"`; and pin it with a semantics assertion (see Finding 3).
3. **Medium — the new UI test does not cover the a11y contract and is not wired into any CI lane.** `StrategyPickerInstrumentationTest` asserts displayed names and the write commit but nothing about radio semantics (`Selected`, `Role.RadioButton`, click action, announcement content), and `grep StrategyPicker .github/workflows/` shows no lane executes it — it compiles in CI but never runs. The Issue's acceptance explicitly names TalkBack/Switch Access/200% font scale for the new selection UI; add semantics assertions (e.g. `assertIsSelected`/`assertRole`/content-description checks) and a font-scale/traversal case, and add the class to the `issue52` lane (same surface).
4. **Medium — write failures are silent at the UI.** `else -> Unit` satisfies "existing selection intact / no new run", but a `WriteFailed`/`BundleUnavailable` result produces no user-visible or announced feedback, so the Issue's "failure 時の既存選択保持が UI 経由で観測可能" is met only passively (the old selection stays displayed). Consider a live-region announcement on rejection/failure; the store-seam tests remain the authoritative evidence meanwhile.
5. **Low — `crossPageMovedCount` counts Workspace→Workspace moves only.** A `Moved(FOLDER_MEMBER)` placement whose new folder lands on another page is not counted, because `PlacementTarget.FolderMember` carries no page (the destination page is the separate `NewFolderChange.placement`). This is a faithful reading of "source and destination pages differ" over the placement vocabulary (spec 194 forbids reinterpreting it), but the spec 182 GLOBAL_COMPACT scenario sentence could be read to include those moves; record the definition in the string or a spec/CONTEXT note so the measure is unambiguous ("moves between screens" currently under-reports folder-bound cross-page moves).
6. **Low — main-thread store read.** `readSelectedStrategy(context)` performs a file read inside `remember {}` during composition (main thread), deviating from the `CategoryOverridePreferences` pattern of `withContext(Dispatchers.IO)` loads; small file, but worth aligning. Related: `strategyCatalog`/selection are read once per composition — a selection changed elsewhere while the screen is open is not re-read (acceptable for this surface; the composer always re-reads).
7. **Low — new trigger for the pre-existing `dismiss()`-during-`Recovering` hazard.** The picker stays clickable during `Recovering`; a committed selection then calls `dismiss()`, which releases the recovery lease while `application.confirmRecovery` is still executing on another IO thread, and `start()` proceeds (the same behavior the back button already had — not introduced here, but this PR widens the entry points). DB safety is preserved by the application-layer transaction + revision/precondition gates; consider gating picker restarts to pre-`Applying` states in a follow-up.
8. **Nit — copy/format.** `organization_strategy_unknown_name` "Custom strategy"/「カスタムストラテジー」 describes a future *built-in* catalog member without a string mapping (misleading label; a neutral "Organization strategy" would fit); the added `manual_organization_strategy_section` line in `values-ja/strings.xml` starts at column 0 (indentation inconsistent with the file; spotless does not police res XML).

**Verdict: NO-GO** at `fefc98dda5`. The data-path contracts are sound — the picker issues only the Rule Management validated write command and never touches storage or an in-run composed input, the fresh dismiss+start cycle matches spec 52's no-snapshot-reuse rule with a safe `ApplicationInProgress` no-restart guard, fail-closed double defense (picker hides active selection on unreadable store while the composer independently returns `NotReady`) is coherent, the new `PreviewCounts` fields derive from the same rows the change list renders (spec 194 one-truth preserved), and the `Summary.organizationStrategy` echo stays out of the diagnostics journal. But the PR ships a deterministic regression of the spec 52 MFO-15 / spec 195 instrumentation suite on its own surface (12 failed tests, `final-status` red on the audited head — the high-risk gate's CI evidence requirement is unmet), and the picker's `contentDescription` suppresses the strategy name from TalkBack announcements against the spec's accessibility contract. Fix Findings 1–2 (plus the Finding 3 test wiring so the lane actually executes the new test), land a green `pull_request` run with `final-status` success on the new head, then re-audit if the fix changes anything beyond this surface's tests/layout; a docs-only commit of this record plus a code fix requires re-audit against the new head per the gate's lineage rule.
