# Test Audit

Use this skill to turn the repository's quality policy into a concrete decision before test code or CI routing grows.

This is an operational procedure, not a new policy source. If this file conflicts with
`AGENTS.md`, `docs/engineering/quality-strategy.md`,
`docs/engineering/ci-test-portfolio.md`,
`tools/repo-contract/ci_portfolio_map.yml`, or `.github/workflows/ci.yml`,
follow those canonical sources and update this skill separately.

Conceptually adapted from OpenClaw's public `test-audit` skill, but the rules,
commands, ownership model, and CI classifications below are NunuLauncher-specific:
https://github.com/openclaw/openclaw/blob/main/.agents/skills/test-audit/SKILL.md

## Select a mode

- **Authoring gate**: use before adding or materially changing a test.
- **Focused audit**: use when reviewing a test, flake fix, test-support seam, or one CI lane.
- **Portfolio campaign**: use only for a bounded subsystem or CI portfolio sweep; Issue #422 and
  `docs/engineering/ci-test-portfolio.md` are the baseline, so do not reopen already-settled
  classifications without new evidence.

## Read first

Before judging coverage, read:

1. The owning Issue, accepted spec/plan when present, and relevant regression history.
2. Root/scoped `AGENTS.md`.
3. The complete production owner and its callers/callees at the boundary under test.
4. Existing tests that can fail for the same regression.
5. `docs/engineering/quality-strategy.md`.
6. For CI work, also read:
   - `docs/engineering/ci-test-portfolio.md`
   - `tools/repo-contract/ci_portfolio_map.yml`
   - the relevant jobs and path filters in `.github/workflows/ci.yml`

Do discovery read-only first. Do not decide that a test is redundant from its name, file,
runtime, or flake history alone.

## Authoring gate

Do not add a new test until every question below has a concrete answer.

1. **Protected contract** — What observable behavior, invariant, failure semantic, or independently
   meaningful compatibility contract does the test protect?
2. **Credible regression** — What plausible production change makes this test fail? For a bug fix,
   demonstrate that the regression test fails on the pre-fix code for the intended reason when
   practical. If pre-fix proof is impractical, record why and what substitute evidence is used.
3. **Canonical owner** — Which test already owns this contract? Prefer one primary regression owner
   at the lowest, fastest, deterministic boundary that can faithfully observe the contract.
4. **Distinct higher-layer risk** — If the same scenario is also tested at instrumentation/UI level,
   name the extra risk that lower layers cannot observe: Android framework integration, process
   recreation, real filesystem/SQLite behavior, Binder/thread affinity, focus/accessibility,
   lifecycle, API-level behavior, or equivalent. Without a distinct risk, extend the primary owner
   instead of replaying the scenario.
5. **Production seam cost** — Does the proposed test require a production export, wrapper, flag,
   global, injection hook, or alternate path that no production caller needs? If yes, move the test
   to the real owning boundary unless the seam has an independent production design reason.
6. **Impact ownership** — Which impact surface owns the test, and which existing CI job should run
   it? If no existing surface/lane fits, explain the missing contract before proposing a new one.
7. **CI classification** — Is the evidence Permanent, Conditional, Scheduled/Diagnostic, or
   Retire/Replace under the #422 model? A test created for one Issue does not automatically become
   a permanent PR gate.
8. **Cost versus confidence** — What independent regression confidence is gained relative to
   runtime, clean-state requirements, flake surface, and maintenance cost? Optimize for confidence
   per CI cost, not for test count, lane count, or deletion count.

Record the answers in the PR when adding new coverage or routing. If an answer is unknown, keep the
test local/diagnostic until ownership is resolved instead of creating a new permanent lane.

## Suspect patterns

Treat these as review triggers, not automatic deletion rules:

- assertion-free execution/coverage probes;
- assertions about private call shape, source layout, method names, or implementation ordering when
  that detail is not externally observable;
- expected values generated by the implementation/helper being tested;
- mocks or fixtures that implement the very behavior being asserted;
- the same regression scenario repeated at unit, instrumentation, and UI layers without a distinct
  layer-specific failure mode;
- tests whose only reason for existence is preserving test-only production code;
- dead production/support code whose remaining callers are tests;
- exact source/string greps when an executable contract is available at similar cost;
- fixed sleeps, widened timeouts, focus retries, or reruns used as the oracle rather than an
  observable state transition;
- capability/flag tests that restate configuration without exercising the promised behavior;
- negative tests that pass because an unrelated guard rejects earlier than the intended path;
- test names that promise a lifecycle/rollback/retirement effect that the fixture never reaches;
- an Issue-number-specific CI lane proposed only because a new test exists.

A behavior-preserving refactor breaking a test is strong evidence that the test is coupled to
implementation. Rewrite it at the owning boundary unless the inspected detail itself is the
independent contract.

## Retention bar

Keep a test when it independently protects a meaningful contract that would otherwise lose
regression detection. Examples include:

- planner/application invariants and failure semantics;
- DB schema migration, downgrade, transaction, recovery, and persistence behavior;
- Launcher3/model writer integration that requires the real framework boundary;
- process death/recreation or cross-process restore;
- platform/API compatibility;
- UI semantics, focus, accessibility, and interaction behavior that cannot be proven below Compose
  or instrumentation;
- security, privacy, permission, serialization, public API, or file-format contracts;
- observable ordering when order affects user-visible or persistence behavior;
- a proven bug regression at its canonical owner boundary.

Static, slow, or flaky is not by itself a deletion reason. First determine whether the contract is
valuable and whether the same proof can live at a more deterministic boundary.

## Focused audit evidence

Before deleting, demoting, moving, or consolidating a candidate, record:

- exact test/class and location;
- the observable failure it can actually detect;
- production owner and non-test callers of any supporting seam;
- overlapping tests and which one is the primary owner;
- historical reason the test/lane exists;
- whether the candidate fails on baseline and, if so, whether that indicates a product defect;
- stronger proof that remains after the change, or why no proof is required;
- production/test-support code that becomes removable;
- impact surface and CI classification before/after;
- focused validation command and residual risk.

If any of these are unclear, do not delete the test merely to simplify the suite.

## CI routing decision

Use this order:

1. Put the regression at the lowest faithful deterministic boundary.
2. Reuse an existing CI lane when its API level, process boundary, storage, fixture isolation, and
   clean-state requirements are compatible.
3. Add the test to an existing impact surface where ownership already matches.
4. Create a new lane only when existing lanes cannot provide the required isolation or runtime
   boundary without weakening another contract.
5. Before a new permanent lane is accepted, explain why Scheduled/Diagnostic execution is
   insufficient for the regression's risk.
6. When routing changes, update `ci_portfolio_map.yml` and
   `docs/engineering/ci-test-portfolio.md` in the same PR as required by the canonical policy.
7. Do not infer execution from a path mapping alone: explicit class filters can leave a test
   unrouted even when its directory belongs to a surface. Verify the actual Gradle/job invocation.

For workflow-only changes, preserve the existing self-exercise rule: the CI configuration change
must not skip the gates whose orchestration it modifies.

## Flake and intermittent failure handling

Follow the six #422 failure classes in `quality-strategy.md` before deciding on retry, quarantine,
or test changes:

1. product regression;
2. deterministic test defect;
3. test synchronization/test harness defect;
4. CI wrapper/artifact handling defect;
5. emulator/runner/platform environment defect;
6. unknown/investigation required.

Capture failure evidence before rerun when the lane supports it. A rerun becoming green does not
classify the failure. Do not weaken an independent contract merely to make CI green; repair the
owner, move the proof to a more deterministic boundary, or track the environment/harness defect
separately.

## Validation

Run the smallest proof first, then the repository checks relevant to the changed surface. For CI
portfolio/routing work, include:

```bash
python3 tools/repo-contract/validate_ci_portfolio.py
python3 tools/repo-contract/test_validate_ci_portfolio.py
python3 tools/repo-contract/validate_repo_contract.py
python3 tools/repo-contract/test_validate_repo_contract.py
```

Run the actual affected Gradle test/filter when test code changed. For workflow changes, rely on the
real GitHub Actions run as the final orchestration evidence; local YAML/string checks are not a
substitute for the workflow executing.

## Handoff

Report:

- protected contract and credible regression;
- canonical owner boundary and why;
- retained/removed overlap;
- impact surface and CI classification;
- whether a production seam or new lane was avoided/added and why;
- flake classification when applicable;
- focused validation actually run;
- unresolved risks or follow-up Issue.
